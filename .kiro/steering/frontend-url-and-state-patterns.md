# フロントエンド URL・状態管理・バリデーション規約

フューチャー株式会社 Webフロントエンド設計ガイドライン（<https://future-architect.github.io/arch-guidelines/documents/forWebFrontend/web_frontend_guidelines.html>）を参考に、本プロジェクトの既存規約（`frontend-rules.md`, `frontend-data-patterns.md`, `rest-api-standards.md`）と矛盾しない範囲で採用した指針。

---

## URL・クエリパラメータ設計

### 名詞ベースのURI（動詞を避ける）

操作を表す動詞（`search`, `get`, `delete` 等）を含むパスを作らない。リソースを表す名詞のみでパスを構成する。

```text
❌ /orders/search?cond1=xxx
❌ /orders/{id}/detail

✅ /orders?status=confirmed
✅ /orders/{id}
```

`rest-api-standards.md` の「URL 設計」（複数形・ケバブケース）と一致する方針。

### クエリパラメータは `?key=value` 形式

`?value` のような値のみのクエリパラメータは使わない。パラメータが増えた際に意味が不明瞭になり、クローラー・ツールでの解析性も落ちる。

```text
❌ /orders/1/products?2
✅ /orders/1/products?productId=2
```

### 同じキーの複数値は繰り返す（CSV結合しない）

```text
✅ /orders/1/products?type=pattern1&type=pattern2
❌ /orders/1/products?type=pattern1,pattern2
```

TanStack Router で扱う場合は `URLSearchParams` 経由でパース・更新する。

### 一時的な値・トラッキング値をURLに含めない

セッションID、タイムスタンプ、ユーザーごとに変わる相対値（`location=nearby` 等）はURLパラメータに含めない。同一ページに対する重複URLの発生や、URLの有効期間短縮につながる。

```text
❌ /orders/1/product?session=452991833
❌ /about?now=12:34am
```

**セキュリティ上の注意**: セッションIDやアクセストークンをパスパラメータ・クエリパラメータに含めない。ブラウザの `Referer` 送信によりリンク先サイトへ漏洩するリスクがある。Cookie または `Authorization` ヘッダーを使う。

## 画面間パラメータ連携（データの保持・受け渡し方式の選択）

画面間でデータを受け渡す方式は、用途に応じて以下から選択する。

| 方式 | 用途 | URLに含む | リロード時 | 適する場面 |
|---|---|---|---|---|
| パスパラメータ | リソースの識別子（ID等） | ✅ | 維持される | `/orders/{orderId}` |
| クエリパラメータ | 検索条件・フィルタ・ページネーション | ✅ | 維持される | 共有・再アクセスしたいデータ |
| オンメモリ（`useState`, TanStack Query キャッシュ） | アプリ内部の一時データ | ❌ | 維持されない | APIレスポンスキャッシュ、URLに見せてはいけないデータ |
| Web ストレージ（`localStorage`/`sessionStorage`） | 長期的な画面共通データ | ❌ | 維持される | ユーザー設定、テーマ |

判断基準:

- **直接リンクで共有・再アクセスさせたい** → パスパラメータ or クエリパラメータ
- **URLで見せてはいけないデータ** → オンメモリ or Web ストレージ
- 検索条件・フィルタ・ソート順は、検索ボタン押下時にクエリパラメータへ反映する（URLで結果を共有できるようにする）

`frontend-data-patterns.md` の「URL 状態 → TanStack Router の search params」方針と一致。

## 状態管理の分類

状態は影響範囲に応じて3種類に分類し、それぞれに適した手法で管理する。

| 種類 | 説明 | 例 | 本プロジェクトでの管理手法 |
|---|---|---|---|
| UIの状態 | 特定コンポーネントに紐づく一時データ | モーダル開閉、フォーム入力値、タブ選択 | `useState`（`frontend-data-patterns.md`参照） |
| アプリケーションの状態 | アプリ全体で共有される状態 | 認証情報、テーマ設定 | React Context（必要になるまで作らない） |
| サーバーの状態 | サーバーと同期が必要なデータ | APIレスポンス、マスタデータ | TanStack Query（Orval 生成 Hook 経由） |

この3分類は `frontend-data-patterns.md` の「サーバーデータ→TanStack Query」「UI状態→useState」「グローバル状態→原則使わない」という既存方針を体系化したものであり、矛盾しない。

### 避けるべきアンチパターン

- **グローバル状態の過剰な使用**: 本来コンポーネント内に閉じられる状態（モーダル開閉等）をグローバルに持ち上げない。変更の影響範囲が不明瞭になり、不要な再レンダリングを招く
- **不必要な状態管理ライブラリの導入**: フレームワーク標準機能（`useState`, Context）で十分な場合に外部ライブラリを導入しない。本プロジェクトは Zustand 等の状態管理ライブラリを導入していない。導入する場合は必要性を明確にしてから

## バリデーション原則

### 入力条件と一致したバリデーションを行う

表示している入力条件（例: 「64文字以下」）より緩い・厳しいバリデーションを実装しない。ユーザーが指示に従ったのにエラーになる状況を避ける。

### クライアントサイド・サーバーサイド両方で実施する

| | クライアントサイド | サーバーサイド |
|---|---|---|
| 目的 | 即時フィードバックによる UX 向上 | データ整合性維持・セキュリティ対策 |
| 実施の要否 | UX 要件次第で省略可 | **省略不可**（クライアント側チェックを迂回された場合の防御） |

サーバーサイドは Bean Validation（`rest-api-standards.md` の Request record 設計）で実施済み。フロントエンドは HTML 制約検証（`required`, `maxLength`, `pattern` 等）とJavaScriptバリデーション（Zod導入時）を併用する。

### ボタンを disabled にしてバリデーションエラーを表現しない

**アクセシビリティの観点**: `disabled` 属性が付いたボタンはキーボード操作のタブフォーカスでアクセスできず、スクリーンリーダーユーザーが位置を把握できない問題がある。

```tsx
// ❌ バリデーションエラー時にボタンを無効化
<Button disabled={!isValid}>送信</Button>

// ✅ 常に有効化し、クリック時にバリデーション結果を表示
<Button onClick={handleSubmit}>送信</Button>
```

**注意**: これは「送信中の二重送信防止」（`isSubmitting` による disabled）とは別の論点。`frontend-ui-patterns.md` のフォームパターンにある `disabled={isSubmitting}` は二重送信防止が目的であり、本項目と矛盾しない。バリデーションエラーの表現は `ErrorMessage` コンポーネント等で行う。

### エラーメッセージの文言

- **具体的にする**: 「エラーが発生しました」ではなく、どうすればよいか分かる文言にする
- **前向きにする**: 「間違っています」ではなく「もう一度入力してください」等、再入力を促す表現にする

```text
❌ エラーが発生しました。フォームを確認してください
✅ パスワードは8文字以上にしてください
```

### インラインバリデーションのタイミング

| チェック種別 | タイミング |
|---|---|
| 必須入力チェック | フォーカスアウト時（未入力のままフォーカスアウトした場合はエラー表示しない） |
| 数値・文字種チェック | HTML の `type` 属性で制御可能なため、入力中チェックは不要 |
| 桁数チェック | 入力中にチェック（例: 自己紹介文の最大文字数） |
| 一致チェック（パスワード確認等） | 確認用入力欄側にチェックを実施 |

いずれも、有効な入力値になった時点でエラー表示を消すことが望ましい。

## 区分値（参照データ）の管理方式

セレクトボックス等のプルダウン項目に使う区分値は、以下のいずれかで管理する:

- backend の enum に対応する固定値 → `frontend-code-patterns.md` の「ステータスラベル・カラー定義」パターンに従い `types/` に定数として持つ（マスタAPIを都度呼ばない）
- 動的に変わる参照データ（DBで管理） → 専用の一覧取得APIから TanStack Query で取得する（Orval 生成 Hook 経由）

固定値か動的値かの判断基準: 「アプリケーションのデプロイなしに値を追加・変更する必要があるか」。必要ならDB管理、不要なら定数管理。

## レスポンシブ対応（Tailwind CSS ブレークポイント）

### メディアクエリファースト、コンテナクエリは必要な箇所のみ

- サイト全体・ページ単位のレイアウト変更（ナビゲーションの切り替え等）→ Tailwind のデフォルトブレークポイント（`sm`/`md`/`lg`/`xl`/`2xl`）を使う
- 個別コンポーネント単位のサイズ依存レイアウト → コンテナクエリ（`@container`, `@sm`, `@md` 等）を使う。多用すると性能・保守性に影響するため、必要な箇所のみに限定する

### モバイルファースト

プレフィックスなしのクラスをモバイル用のデフォルトとし、大きい画面ではプレフィックス付きで上書きする。

```tsx
// ✅ プレフィックスなし = モバイル、sm以上で上書き
<div className="text-center sm:text-left" />

// ❌ sm をモバイルターゲットに使う（Tailwindの設計と逆）
<div className="sm:text-center" />
```

### ブレークポイントの命名

デフォルトの `sm`/`md`/`lg`/`xl`/`2xl` を基本とし、独自ブレークポイントを追加する場合も命名は簡潔で直感的にする（`mobile`/`tablet`/`desktop` 等）。既存プレフィックスの意味を変える上書き（例: `sm` を極端に大きい値にする）は避ける。
